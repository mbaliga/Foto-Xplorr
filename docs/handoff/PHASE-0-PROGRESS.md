## Decisions

- Branch name substitution (above), forced by the harness's fixed per-repo branch assignment.
- (P0-07) `mediaStoreRelativePath` takes an explicit `sdkInt: Int = Build.VERSION.SDK_INT` parameter
  rather than reading `Build.VERSION.SDK_INT` directly, purely so `MediaStoreDestinationTest` can
  exercise both sides of the `Recordings`/API-31 gate. This sandbox has no emulator and only one
  Robolectric framework jar cached offline (confirmed empirically: a `@Config(sdk = [30])` test
  failed on a network fetch this environment cannot make), so simulating a second API level through
  Robolectric itself was not an option here, unlike every other API-gated test in this repo (all of
  which use `sdk = 34` and never assert the pre-gate branch of their own `Build.VERSION.SDK_INT`
  check). Every real caller still just gets the platform's actual value via the default.
- (P0-07) `AudioAsset` gained a `relativePath: String?` field (`= null` default) so
  `AudioConversionWriter` could be wired to `mediaStoreRelativePath` at all — it previously carried
  no `RELATIVE_PATH` from MediaStore whatsoever. Defaulted rather than required, and the scanner
  populates it only from API 29 (matching the photo/video scanner's own existing `RELATIVE_PATH`
  gate); no other construction site exists in `app/src/main` or `app/src/test` for this data class,
  so nothing else needed updating for the new field.
- (P0-08, item 2) "Check what MediaProvider does when a redacted file is opened for writing" —
  the brief's own explicit research ask. `developer.android.com/training/data-storage/shared/media`
  only documents the READ side of `setRequireOriginal`/`ACCESS_MEDIA_LOCATION`, nothing about
  writes. The actual mechanism is `android.os.RedactingFileDescriptor`
  (`android.googlesource.com/platform/frameworks/base/+/master/core/java/android/os/RedactingFileDescriptor.java`),
  whose own javadoc says: "Open the given File and returns a ParcelFileDescriptor that offers a
  redacted view of the underlying data. If a redacted region is written to, the newly written data
  can be read back correctly instead of continuing to be redacted." This confirms redaction is a
  real FD-level wrapper MediaProvider can apply to an opened file regardless of read/write mode,
  and that `ExifInterface.saveAttributes()`'s own read-modify-write cycle (it reads every existing
  attribute before rewriting the whole segment) would read a redacted-away GPS tag as absent and
  then write the segment back without it — a real erasure risk, not a hypothetical one. This
  sandbox cannot inspect MediaProvider's own server-side `openFile` call sites to confirm exactly
  when it chooses to wrap a descriptor this way, so the chosen behavior (refuse entirely without
  `ACCESS_MEDIA_LOCATION` on API 29+, per the brief's own item 2 instruction) stays the fail-closed
  one rather than a narrower one this task could not fully verify.
- (P0-08, item 1) `MetadataWriter.writeBatch` ("bulk metadata edits", named in the brief's item 1)
  has no caller anywhere in `app/src/main` — grepped, confirmed absent, not overlooked. There is
  currently no UI surface for a multi-select metadata batch edit to wire `isMetadataWritable`'s
  pre-flight check into. `write` itself (called by both the single-asset UI path and, internally,
  `writeBatch`) still refuses via item 2's own permission gate regardless, so a HEIC in a
  hypothetical future batch edit would fail safely, just without the "before consent" UX polish
  item 1 asks for specifically. Left as a gap to close when that feature actually gets built.
